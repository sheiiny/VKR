# Объект автоматизации и обоснование темы

## Рекомендуемое решение

Объектом автоматизации предлагается считать **процесс регистрации и отражения выдачи и возврата инструмента в корпоративном учёте предприятия на участке, использующем автоматизированный инструментальный шкаф MATRIX-TM**.

Название реального подразделения и его организационные границы предстоит установить при обследовании. Пока нельзя заявлять, что выбран конкретный цех или инструментально-раздаточная кладовая.

Эта формулировка соответствует задаче исходного ТЗ: исключить повторный ручной ввод локальных операций шкафа в ERP (§ 1.2, 2.1.1, 3.1). При этом она не расширяет работу до разработки всей системы инструментального обеспечения предприятия.

## Почему выбран этот объект

| Вариант | Что можно обосновать | Ограничение |
|---|---|---|
| Инструментальный шкаф целиком | Есть физический объект и штатная автоматизация | Проект не разрабатывает управление замками, датчиками и выдачей |
| Защищённый обмен данными | Точно описывает интеграционные функции | Без производственного контекста трудно объяснить пользу автоматизации |
| Регистрация и отражение выдач и возвратов в учёте | Есть участники, исходное событие, ручная операция и проверяемый результат | Требует уточнить правила учёта в ERP |
| Инструментальное обеспечение всего предприятия | Широкая производственная задача | Включает закупки, ремонты, планирование и списание, которых нет в проекте |

Рекомендуется третий вариант. Защищённый обмен — автоматизируемая информационная часть этого процесса; шкаф, ITM и ERP — его техническое окружение.

## Формулировки для руководителя

**Тема для согласования:** «Автоматизация учёта движения инструмента на основе интеграции MATRIX-TM с ERP-системой предприятия».

**Более узкое название:** «Разработка подсистемы автоматизированного учёта выдачи и возврата инструмента при интеграции MATRIX-TM с ERP-системой».

**Объект исследования:** процесс учёта выдачи и возврата инструмента на производственном участке, использующем MATRIX-TM.

**Предмет исследования:** способы согласования данных шкафа и ERP, подтверждения обработки, защиты обмена и предотвращения повторного проведения операций.

**Цель:** разработать и проверить на учебном стенде интеграционную подсистему, обеспечивающую автоматическое отражение зарегистрированных выдач и возвратов в демонстрационном учёте без повторного ручного ввода.

Формулировки являются предложением. Утверждённая тема и требования кафедры к объекту и предмету имеют приоритет после согласования.

## Текущий и целевой процессы

Текущий процесс ниже — рабочая модель по постановке ТЗ, а не результат выполненного обследования. Не установлены фактические исполнители ручного переноса, его периодичность, объём и доля ошибок.

| Этап | По постановке проблемы | В предлагаемом решении |
|---|---|---|
| Выдача или возврат | Сотрудник выполняет операцию у шкафа | Штатная операция сохраняется |
| Локальная регистрация | MATRIX-TM записывает операцию | Агент читает согласованный источник |
| Подготовка записи для ERP | Возможен повторный ручной перенос | Создаётся единое событие с постоянным номером |
| Корпоративный учёт | Данные вводятся или загружаются отдельно | ERP запрашивает события и проводит движения |
| Проверка результата | Порядок предстоит уточнить | Успешные операции подтверждаются ACK |
| Сбой связи | Порядок восстановления предстоит уточнить | Неподтверждённые события сохраняются для повторного получения |

## Вход, результат и участники

Вход — зарегистрированная шкафом операция: сотрудник, инструмент, ячейка, количество, тип действия и время. Дополнительно используется снимок наличия в шкафу с временем актуальности.

Результат — запись движения в корпоративном учёте либо диагностируемое состояние, требующее разбора. Сам факт выдачи данных API ещё не означает успешный учёт в ERP.

Сотрудник выполняет физическую операцию; шкаф регистрирует её; агент готовит данные; система обмена хранит и выдаёт их; ERP отвечает за проведение; оператор разбирает исключения; администратор поддерживает инфраструктуру.

## Границы разработки

В проект входят получение записей, нормализация данных, постоянные идентификаторы, сопоставление кодов, устойчивое хранение, API, права доступа, подтверждения и журналирование.

Механика шкафа, управление ячейками, разработка ERP и изменение её бизнес-правил остаются вне разработки (§ 3.5). Способ отражения выдачи может быть перемещением, выдачей под ответственность или другим движением по правилам предприятия; его нельзя заранее объявлять списанием всего инструмента.

## Чем обосновать актуальность

По ТЗ локальная регистрация в шкафу не устраняет необходимость повторного корпоративного учёта. Автоматизация этой границы позволяет уменьшить ручной ввод, сделать состояние обмена наблюдаемым и проверять согласованность данных. Конкретное влияние на производство и затраты требует обследования и измерений.

Инженерная сложность — в сохранении одной бизнес-операции при нескольких попытках доставки, восстановлении после перезапуска и правильном распределении ответственности между системами. Использование REST само по себе не является научной новизной.

## Как измерить результат

| Показатель | Как проверить | Статус |
|---|---|---|
| Число повторных ручных вводов | Провести 10 операций через полный цикл без ручного переноса | Критерий § 2.1.1, ещё не проверен |
| Число повторных движений | Повторить получение и ACK после имитации обрыва | Ожидается 0 повторных проведений |
| Полнота учёта | Сверить исходные операции, события и движения демонстрационной ERP | Предлагаемая проверка |
| Задержка | Замерить время от записи источника до сохранения и проведения | Требования § 4.1.4; фактических замеров нет |
| Сохранность | Перезапустить компоненты с неподтверждёнными событиями | Будущее испытание |

Для оценки трудозатрат: `экономия времени = N × (t_ручного_переноса − t_контроля_после_автоматизации)`, где N — число операций за выбранный период. Показатели берутся из наблюдений; числовая экономия сейчас не установлена. Стоимость разработки и сопровождения учитывается отдельно.

2. Допускается ли подтверждение решения на учебном стенде без доступа к оборудованию.
3. Кто может предоставить описание ITM и подтвердить существующий процесс.
4. Какие правила проведения и сопоставления должен воспроизводить демонстрационный ERP-клиент.
